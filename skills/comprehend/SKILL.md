# comprehend

対象の背景・仕組み・設計理由・成立条件・周辺への影響を、人間が自分の言葉で説明し、条件変更にも応用できるようにする。対象の前提と分岐を調べ切る責任はエージェントが負う。調査の完了と、人間の理解の確認を別々の証拠で管理する。

`$comprehend` または「この変更の理解を固めたい」などの依頼で使う。普通の「説明して」だけではこの学習ループを開始しない。厳格な口頭試験を求められたら支援の仕方の違いを明示して扱い、固定の試行回数や合否表現をこの既定へ持ち込まない。

## 1. 対象を調べ、概念を整理する

指定されたPR・ファイル・ディレクトリ・概念を扱う。指定がなければ現在のセッションや差分を候補にし、明確な対象がなければ一度尋ねる。特定のIDEやPR取得機能に依存せず、ローカル資料やユーザーが渡した本文も使える。

全体探索を始める前に [前提と分岐の探索](references/assumption-coverage.md) を読む。仕様、実装、テスト、履歴、呼出し・利用側を横断し、対象全体の骨格を把握する。調べられる事実は自分で調べ、学習者に未知の枝を挙げさせることを前提にしない。

説明・文章作成の指針は、ユーザーが指定した代替スキルや指示があれば、それを採用する。代替指定は japanese-writing の担当範囲全体を置き換え、同梱指針の読込み・適用・照合を必須にしない。併用が明示された場合だけ併用する。指定されたスキルを利用できない場合は、その事情を伝えて代替資料を確認し、同梱指針へ黙って切り替えない。指定がなければ、日本語の説明を組み立てる前に同梱の [説明指針](references/japanese-writing/guidelines.md) と [技術説明](references/japanese-writing/technical.md) を読む。説明指針の差替えは、本スキルの調査・自由回答による理解確認・進捗記録の手順には適用しない。説明の構成・順序・表現は、選択した説明指針に従う。同梱指針を使う場合は、最初に必要な概念・関係・学ぶ順序を短く示し、その後は前提から順序立てて一論点ずつ教える。

見取り図の後、現在の理解を一問で尋ねる。初見または「先に説明して」との希望があれば省略する。自己申告は開始位置の調整に使い、確認済みの根拠にはしない。概念や依存の誤りが見つかれば見取り図も直す。

## 2. 到達点・学習単位・保存先を決める

何を説明・判断できるようになりたいかを提案し、今回の到達点と範囲を合わせる。背景、設計理由、境界、下流影響を含め、観測可能な言葉で示す。

学習単位は一つの機構・設計判断など、理由と条件変更の影響を説明できるまとまりにする。コード行や用語一個ずつの試験に分解しない。対象内の必要な前提・分岐の判定は、調査したエージェントが根拠を示して担う。

保存先は学習開始時にユーザーと決め、一つの進捗Markdownを作成または再開する。既存記録は内容と対象を確認して再利用する。

この段階の完了条件は、対象・資料・現在地・到達点・学習単位・保存先が定まっていること。資料整理だけで人間の理解を認定しない。

## 3. 全体探索を進め、確認問題を準備する

参照の手順に従って主張→前提→分岐を展開し、関連する枝を未処理キューで追う。優先順位は調べる順序に使い、低順位を省く理由にしない。分かった独立部分から教育を進めつつ、全体調査を継続してよい。

単位の前提や問題を見直すときも [前提と分岐の探索](references/assumption-coverage.md) を確認する。単独条件だけでなく、共有状態・順序・契約等に関係する組合せを調べる。代表問題は人間の負担を調整する方法であり、調査の打切り理由ではない。

枝と学習上必要な区別を問題へ対応付ける。結論が変わる、不変、追加情報が必要という区別を扱い、既存問題で兼ねられない必須の区別は追加する。全枝を同じ粒度で一問ずつ出題する必要はない。

出題前に採点要素を資料の箇所へ対応付ける。資料の版・適用範囲の衝突は調べ、なお決められない優先関係だけユーザーに尋ねる。観測事実と推測の設計理由を分け、根拠のない意図を正答にしない。必要な根拠がない問題は、調査するか未解決として採点を保留する。

## 4. 教え、理由と応用を確認する

選択した説明指針に従って、必要な概念、動作、設計理由、成立条件を説明する。同梱指針を使う場合はこの順に一論点ずつ扱う。説明する主張は資料の正確な箇所へ対応付ける。説明の形式にかかわらず、以下の理解確認は学習単位ごとに行う。

単位ごとに、理由の説明と条件変更への応用を別々の短い自由回答問題で確認する。一度に一問を出して回答を待つ。変える条件と維持する条件を明確にし、実行順などで結果が分かれるなら、特定の順序か、起こり得る結果・保証を問うのかを示す。回答前に正答や核心の手がかりを明かさない。特定の質問UIを前提にしない。

回答を資料、因果関係、成立範囲、変更の影響に照らして判定し、何が説明でき、何が不足かと根拠の資料箇所を短く示す。用語の一致を求めない。「わかった」という申告や選択肢だけでは確認済みにしない。判定への異議は、問題・採点・資料の解釈も含め再検討する。

不足があれば欠けた前提を調べ、ヒント、別の説明、例で補う。核心となる因果・理由・答えをヒントで与えた場合は、同じ原理で意味のある条件を変えた別問題を出す。合意した到達点内の難度で、答えの手がかりなしに理由を説明できてから確認済みにする。表現の確認だけで機械的に追加試験を増やさず、単なる言い換えの問題を応用の再確認に使わない。

停滞したら説明方法や前提の分解を変え、休止・再訪を選べるようにする。固定3回制限や毎問の継続確認は設けない。同じ失敗を際限なく反復せず、回答がない間に自動で次へ進まない。未確認の前提に依存する後続を理解済みとして進めない。独立した単位へ移る場合は未確認を残す。

単位のチェックは、必要な理由・応用の区別を人間が正しく説明した証拠が揃ってから付ける。教えたことや問題を作成したことだけではチェックしない。

## 5. 全体確認・保存・中断

単位の確認後に、全体をつなぐ説明と条件変更への応用を一問ずつ確認する。対象全体の調査が参照の基準で完了し、必要な単位・区別と最終確認に理由を伴う正しい回答の証拠が揃って、今回の範囲を完了とする。最終問題で単位の確認を代用しない。

進捗は単位の確認時、範囲や調査状態が変わった時、中断・完了時に更新する。

| 記録 | 保存する内容 |
|---|---|
| 範囲 | 対象、資料の版・箇所、到達点、単位、範囲変更と裁定 |
| 全体調査 | 境界の根拠、資料の所在、入口から出口の対応、資料と木の照合結果 |
| 分岐 | 主張、前提・組合せ、依存先、根拠と結論、葉を閉じた理由、未処理キュー |
| 外的障害 | 調査場所、障害、代替確認の試行、不足情報、影響、再開条件 |
| 回答 | 問題、回答要旨、判定根拠、核心ヒントの有無、確認日 |
| 現在地 | 調査と学習の別々の状態、弱点、範囲外候補、次の調査・次の一問 |

問題候補の探索済み・検証済み・人間の回答確認済みを区別する。回答全文の複製は基本にせず、必要な要旨を残す。具体的な再確認項目と持続的な誤解を区別し、専用ファイル群を必須にしない。コミットは自動で行わない。

中断はいつでも受け入れ、途中・休止の状態と次の一手を保存する。人間が応答しない実行では資料整理と検証待ちを分け、人間の理解を自己認定しない。終了禁止や `/goal` に依存しない。

## 6. 再開・再確認から再完了へ

同じ対象の再開時に記録と資料の版を確認する。資料変更が前提を崩すなら、影響する調査と確認を見直す。以前つまずいた重要点は同原理・同程度の難度の短い問題で、答えの手がかりなしに確認する。

過去の確認日・成功は履歴として保持する。今回不足が出た単位と、その前提に依存して影響する単位を未確認、今回の学習を途中へ戻す。依存の向きと判断根拠を記録し、影響のない証拠は維持する。関係が不明なら調べる。次の一問は欠けた前提または当該単位から選ぶ。

通常の説明・理由・応用確認を再適用し、核心ヒント後の別条件問題も同じ規則に従う。必要な単位が再び確認済みになったら最終統合確認を再実施する。最終確認が通らなければ不足する単位・前提を補い、別の統合問題で確認する。最終確認だけの不足なら単位の成功証拠を保持してもよいが、最終確認は未確認に戻す。証拠が揃ってから今回を完了へ戻す。

後日の再確認はユーザーが開始した学習内で行う。確認済みは日付付きの証拠であり、通知・定期実行や永久的な能力認定を意味しない。
